# Contributing to localhost

Thanks for helping. This guide covers building, testing and what a change needs to be merged. How the code is organised, the words it uses and the rules every change keeps are in [AGENTS.md](AGENTS.md): read it before your first change.

For anything larger than a small fix, open an issue first so we can agree on the approach before you write it.

## Building

Requirements for the macOS app: macOS 15 or later, Xcode 26 (Swift 6.2), and Rust through [rustup](https://rustup.rs). The Linux and Windows app needs Rust, Node.js 22+ and pnpm (see "The Linux and Windows app" below).

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
rustup target add aarch64-apple-darwin x86_64-apple-darwin   # the app ships for both
```

The repository's layout is in [AGENTS.md](AGENTS.md#repository).

### The macOS app

Once after cloning, build the core so Xcode finds the package's library:

```sh
scripts/build-core.sh debug
```

Then open `apps/macos/localhost.xcodeproj`, select the `localhost` scheme and press ⌘R. The scheme rebuilds the core before every build (debug for Debug, universal for Release). Xcode doesn't show that step's output: if the build stops at "Check the Rust core", the reason is in `apps/macos/LocalhostCoreFFI/Generated/build.log`, or run `scripts/build-core.sh` in a terminal. Or from the command line:

```sh
xcodebuild -project apps/macos/localhost.xcodeproj -scheme localhost -configuration Debug -derivedDataPath build build
open build/Build/Products/Debug/localhost.app
```

Without a signing identity, add `CODE_SIGNING_ALLOWED=NO` (CI does). A build signed that way, or ad hoc, asks for Keychain access to Secrets after every rebuild; see "Keychain prompts" in the README.

To try a build without touching your real data in `~/Library/Application Support/localhost`, point it at another folder:

```sh
open -n --env LOCALHOST_STORAGE_ROOT=/tmp/localhost-dev build/Build/Products/Debug/localhost.app
```

Secrets still go to your login Keychain, under the service `io.github.marcellosso.localhost.secret`.

### The core

The core builds and tests on its own, without the Xcode project, on macOS and Linux (`core/README.md`):

```sh
cd core
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt
```

The Windows app links the core too, so it must also compile for Windows. Check it from macOS or Linux (clippy doesn't link, so no Windows toolchain is needed):

```sh
rustup target add x86_64-pc-windows-msvc
cargo clippy -p localhost-core -p localhost-cli --target x86_64-pc-windows-msvc --all-targets -- -D warnings
```

On Windows, a Project runs either on Windows itself, through `cmd.exe` in a Job Object, or in a WSL distro. Windows CI runs the lib tests and `tests/process_tree_windows.rs` against real processes.

The Swift layer has its own tests, which need the library built first:

```sh
scripts/build-core.sh debug
cd apps/macos/LocalhostCoreFFI && swift test
```

### The Linux and Windows app

`apps/desktop/` is a Tauri 2 app: a Rust shell in `src-tauri/` that hosts the core, and a React + TypeScript UI in `src/`. It runs on macOS too for development, but only ships for Linux and Windows. On Linux, first install the webview and tray libraries ([Tauri's prerequisites](https://v2.tauri.app/start/prerequisites/)), e.g. on Ubuntu:

```sh
sudo apt install libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev libxdo-dev libssl-dev
```

Then:

```sh
cd apps/desktop
pnpm install
pnpm tauri dev                      # the app, reloading as you edit
pnpm typecheck && pnpm test         # TypeScript and Vitest
cd src-tauri && cargo test          # Rust tests; also regenerates src/bindings.ts
scripts/log-perf.sh [services] [lines/s each] [seconds]   # log view frame times and memory
```

The log view must stay smooth with very chatty Services, on WebKitGTK above all (AGENTS.md, Performance). `scripts/log-perf.sh` runs the app in a measurement mode against a throwaway Project and prints frame times (p50, p95, max, frames over 33 ms) and peak memory. Run it on Linux before and after changing anything on the log path, and put the numbers in the PR.

The UI talks to Rust only through `src/bindings.ts`, generated by tauri-specta from the commands in `src-tauri/` and the core's types (its `specta` feature). Don't edit it: after changing a command or a core type the UI sees, run `cargo test` in `src-tauri/` and commit the result. CI fails if it is out of date. `cargo test` and `cargo clippy` there need `dist/`, so run `pnpm build` once first.

On macOS its data goes to `~/Library/Application Support/localhost-desktop`, apart from the macOS app's, and on Windows to `%APPDATA%\localhost`; `LOCALHOST_STORAGE_ROOT` points it anywhere else. Release builds on Windows turn WebView2's browser keys off (F5, Ctrl+P, Ctrl+F, F12…); debug builds keep them, for the developer tools. Outside text fields and selected text, release builds also hide the webview's own right-click menu (Reload, Back, Inspect). Colours live in `src/styles/tokens.css`, with the same values as `apps/macos/App/Views/Theme.swift`: change both together.

The app reaches every Service through `Targets` (AGENTS.md, Architecture). This machine is the shared core (a named pipe on Windows), which the app starts from its own executable (`--daemon <storage root>`) and `localhost mcp` from `localhost daemon`; a development build with `LOCALHOST_STORAGE_ROOT` gets a core of its own, as each storage root does. On Windows a WSL Project runs in the `localhostd` inside its distro. To try that path without Windows, point `LOCALHOST_DEV_LOCALHOSTD` at a `localhostd` binary: every Project, this machine's included, then runs through one started by the app, one per Execution Target, keeping its logs in `<storage root>/localhostd/<target>`.

```sh
(cd ../../core && cargo build -p localhost-daemon)
LOCALHOST_DEV_LOCALHOSTD=$PWD/../../core/target/debug/localhostd pnpm tauri dev
```

On Windows the app lists the WSL distros (`wsl.exe --list`), and Add Project asks which one a Project runs in; a folder picked under `\\wsl.localhost\<distro>` runs in that distro. The first time a distro is needed, the app copies its `localhostd`, a Linux build, into `~/.local/share/localhost/windows/` there, named after the app's version and a hash of the binary, and runs it with `wsl.exe`. That folder also keeps the distro's logs and Run records. A release has `localhostd` beside the app. In development, build it in a distro and point `LOCALHOST_WSL_LOCALHOSTD` at it (static, so any distro can run it):

```sh
# in WSL, in the repository's core/ (needs `rustup target add x86_64-unknown-linux-musl` and musl-tools)
cargo build -p localhost-daemon --target x86_64-unknown-linux-musl
```

```powershell
# in PowerShell, in apps\desktop
$env:LOCALHOST_WSL_LOCALHOSTD = "\\wsl.localhost\Ubuntu\home\me\localhost\core\target\x86_64-unknown-linux-musl\debug\localhostd"
pnpm tauri dev
```

Checking the app for Windows from macOS or Linux works like the core's check above, run in `src-tauri/`. It also needs `llvm-rc`, LLVM's resource compiler, on the `PATH`: Tauri's build script compiles the Windows icon with it.

## Pull requests

1. Branch from `main`, one topic per branch.
2. Run the checks for what you touched (AGENTS.md, Verifying a change), then build and run the app.
3. Open a PR describing what changed and why, how you checked it, and anything you left out. Link the issue it addresses.

CI runs the core's tests on Linux, macOS and Windows, the Swift layer's tests, an unsigned app build, and the desktop app's checks (TypeScript, Vitest, clippy, its Rust tests, up-to-date bindings); all must pass. On a PR each job runs only when files it depends on changed, and is skipped otherwise: the core's jobs for `core/` and `skills/` (the core embeds the localhost-mcp skill), the macOS job for those and `apps/macos/`, the desktop job for those and `apps/desktop/`, and each for the scripts it runs. The site builds only for `site/`, `docs/`, `.github/assets/` and the desktop tokens. Changing a workflow runs everything in it, and every push to `main` runs everything; release packages are built only by a release tag. A skipped job counts as passing, and the `CI result` check fails if any CI job failed. The macOS job also skips draft PRs (macOS minutes cost the most), so mark yours ready for review when you want the full run. CI on a PR from a fork starts once a maintainer approves the run, and every PR needs a maintainer's approving review before it merges. Commits are kept as written (merge commits, no squash), so make each commit message say what it does in one line.

Releases are cut by tagging `main`; see [RELEASING.md](RELEASING.md).
